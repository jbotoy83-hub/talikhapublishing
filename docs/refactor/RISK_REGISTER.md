# Risk Register — Talikha Publishing Refactor

**Last updated:** 2026-07-31
Risks are rated **Likelihood** (L/M/H) × **Impact** (L/M/H). Security and data-integrity risks are treated as high priority regardless of score. Sources: `.planning/codebase/CONCERNS.md` (2026-07-30 audit), baseline investigation (2026-07-31).

> Refactor rule: security fixes may change defective behavior, but each must be **isolated, documented, tested, and reported separately** from ordinary refactoring (master instruction §9, §12). None of these are addressed during baseline.

## A. Security risks (Phase 9 — isolated, documented fixes)

| ID | Risk | Files | L×I | Notes / mitigation direction |
|----|------|-------|-----|------------------------------|
| SEC-1 | **Admin dashboard missing role check — FIXED (2026-07-31).** `/api/admin/dashboard` used a bare `getAdminUser()` presence check (no role check), so an authenticated `viewer` could read all editorial data via service-role (which bypasses RLS). | `src/app/api/admin/dashboard/route.ts` | M×H | **Fixed:** now guarded by `requireEditorApi()` + `isApiError` (admin/editor only; viewer→403, anonymous→401). **Note:** the endpoint has **no in-repo callers** (the admin SPA uses `/api/admin/workspace`) — likely legacy; owner to confirm whether to keep or remove it. Still TODO: audit every `/api/admin/*` handler for a guard. |
| SEC-2 | **Hardcoded admin allowlist bypass — FIXED (2026-07-31, owner-confirmed).** `jbotoy83@gmail.com` was always in the admin set, independent of `ADMIN_EMAILS`; authenticating as that address auto-promoted the profile to admin. | `src/lib/auth.ts` (`configuredAdminEmails`); `docs/DEPLOYMENT.md` | M×H | **Fixed:** the hardcoded address was removed from `configuredAdminEmails()`; the allowlist now comes solely from `ADMIN_EMAILS` (or `profiles.role = 'admin'`). The launch-readiness gate already requires `ADMIN_EMAILS` for production. Owner confirmed their admin access is preserved (email in `ADMIN_EMAILS` and/or profile role `admin`) before removal. Docs (`DEPLOYMENT.md`) and the codebase map (`INTEGRATIONS.md`, `CONCERNS.md`) updated. Cosmetic SPA display fallbacks using that email (`admin-panel/src/main.tsx`) remain — not a security issue; optional later cleanup. |
| SEC-3 | **Viewer can upload workflow files — ALREADY MITIGATED (verified 2026-07-31).** The 2026-07-30 audit was stale: `workflow-files` `POST` (line 44) and `DELETE` (line 153) both already call `requireEditorApi()` + `isApiError`, rejecting viewers (403) and anonymous (401). | `src/app/api/admin/workflow-files/route.ts:44,153` | — | Verified guarded; no change needed. |
| SEC-4 | **Reference-only tracking exposes private artifacts — ACCEPTED with mitigation (owner decision, 2026-07-31).** `/api/track` accepts a reference/tracking/receipt number and returns author-visible events + 1-hour signed file URLs + certificate URLs. The reference has an 8-hex random suffix. | `src/app/api/track/route.ts` | M×H | **Owner decision:** keep reference-only access to both status and files (no second factor added), preserving the current author UX. **Mitigation in place:** distributed rate limiting is now mandatory for production (SEC-5: 5 lookups / 15 min per IP via Upstash Redis), which makes brute-forcing the 8-hex reference impractical; responses are `private, no-store`. **Residual risk (accepted):** anyone who obtains or guesses a valid reference can still retrieve that submission's files/certificates; a second factor (author email/OTP) was declined. Revisit if references are ever leaked or stronger author authentication becomes a requirement. |
| SEC-5 | **Rate limiting fails open without Redis — MITIGATED (2026-07-31; policy: require Redis + fail-open + log).** When Upstash vars are absent, `allowRequest()` returns `true`; the five abuse-sensitive public endpoints (submissions init/complete, track, track-respond, search) then have no effective distributed limit. | `src/lib/rate-limit.ts`; `scripts/check-launch-readiness.mjs`; `.env.example` | H×M | **Mitigated (owner-chosen policy):** (1) `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are now required by the production launch-readiness gate, so a production deploy cannot pass without Redis configured; (2) runtime stays **fail-open** to preserve availability (a Redis outage won't block legitimate submissions); (3) `allowRequest()` now logs a one-time `[rate-limit]` warning when Redis is absent, so the fail-open is visible rather than silent. **Residual risk / future options:** a runtime Redis outage still disables limiting until restored; stronger options (fail closed everywhere, fail closed for submissions only, or a Vercel platform limiter) were declined for now. (The per-instance `Map` is only a limiter cache; counts live in Redis, so that was never the issue.) |
| SEC-6 | **Implicit local admin bypass — FIXED (2026-07-31).** Any non-production process without a service-role key got a synthetic admin from `getAdminUser()` (the `if (!getSupabaseAdmin()) return true` fallback), so a misconfigured staging/preview env could expose admin APIs. | `src/lib/auth.ts` (`isLocalAdminBypassEnabled`) | L×H | **Fixed:** removed the implicit `!getSupabaseAdmin()` fallback; the bypass now requires an explicit `LOCAL_ADMIN_BYPASS=true` and is forced off in production (also already forbidden by the readiness gate). Staging/preview now fail closed. `.env.example` and the codebase map updated. **Not done (optional further hardening):** restrict the bypass to loopback requests — requires threading request context into `getAdminUser()`, a larger change. |
| SEC-7 | **Undocumented `CRON_SECRET` — FIXED (2026-07-31).** `/api/cron/journal-lifecycle` requires `CRON_SECRET` in production but `.env.example` omitted it; a deploy without it silently 401s the Vercel cron and stops lifecycle work. | `.env.example`; `scripts/check-launch-readiness.mjs`; `src/app/api/cron/journal-lifecycle/route.ts:5-9` | M×M | **Fixed:** `CRON_SECRET` is now documented in `.env.example` (with the Vercel auto-Bearer behavior explained) and added to the production launch-readiness `requireValue` list, so a missing secret now fails the readiness gate loudly instead of silently stopping the cron. **Unrelated pre-existing bug left as-is:** the readiness script still checks the wrong Supabase var names (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`/`SUPABASE_SECRET_KEY` vs the runtime `NEXT_PUBLIC_SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`) — a separate issue, not touched here. Remaining: monitor cron failures/lifecycle freshness in production. |
| SEC-8 | **Viewer read access to workspace + files — FIXED (2026-07-31, owner-approved).** `/api/admin/workspace` and `/api/admin/files/[id]` used `getAdminUser()` with no role check, so an authenticated `viewer` could read all editorial data (submissions incl. author emails + payment metadata, publication records, certificates, media) and download any submission file. | `src/app/api/admin/workspace/route.ts`; `src/app/api/admin/files/[id]/route.ts` | M×H | **Fixed (owner decision: viewers should NOT read editorial data):** both routes now use `requireEditorApi()` + `isApiError` (editor/admin only; viewer→403, anonymous→401). Editor/admin success and demo-mode responses are unchanged. **Follow-up (UX, not security):** the admin SPA handles 401 explicitly but not 403, so a viewer now falls back to prototype/local data rather than an "access denied" message; the `/admin` middleware also checks authentication only, not role. Consider a clearer viewer redirect/message later. |
